# Поиск неполного состояния Salsa20 на CUDA

Необязательная утилита перебирает неизвестные байты **полного 64-байтного состояния Salsa20/20**. Это не перебор паролей: стандартное развёртывание ключа не выполняется. Для проверки нужен известный префикс потока — XOR шифротекста и предполагаемого открытого текста.

## Сборка и проверки

Для GPU-сборки нужны NVIDIA GPU, совместимый драйвер, CUDA Toolkit с `nvcc`, компилятор C++17 и `make`. Рабочая платформа GPU — Linux. Целевую архитектуру укажите явно; по умолчанию Makefile использует `sm_80`:

```sh
make CUDA_ARCH=sm_89
```

Для RTX Blackwell используйте `make CUDA_ARCH=sm_120` и CUDA Toolkit 12.8 или новее. Опции компилятора можно передать через `CXX`, `CXXFLAGS`, `NVCC` и `NVCCFLAGS`.

CPU-тесты не требуют CUDA и видеокарты:

```sh
make test
python3 -B -m unittest -v test_search_runner.py
make clean
```

Тесты C++ проверяют аргументы, границы диапазонов, три эталонных блока Salsa20 и все 64 позиции байтов. Тесты Python используют имитацию исполнителя и проверяют продолжение поиска, границы шардов, ошибки и остановку процесса. В этой копии локально проверены только CPU-тесты на macOS; сборка и запуск GPU локально не выполнялись.

## Команды

```text
./salsa_search search STATE_HEX OFFSETS_CSV TARGET_KEYSTREAM_HEX START COUNT [BATCH_COUNT] [MAX_SECONDS] [DEVICE] [THREADS]
./salsa_search blocks STATE_HEX OFFSETS_CSV START COUNT [DEVICE]
```

| Аргумент | Значение |
|---|---|
| `STATE_HEX` | Ровно 128 hex-символов, то есть 64 байта состояния |
| `OFFSETS_CSV` | От 1 до 5 уникальных смещений байтов 0..63, например `59,60,61,62,63`; это список неизвестных позиций, а не битовая маска |
| `TARGET_KEYSTREAM_HEX` | От 1 до 64 начальных байтов ожидаемого потока в hex |
| `START`, `COUNT` | Десятичные целые числа; проверяется полуинтервал `[START, START+COUNT)` внутри `0..2^(8*N)`, где `N` — число неизвестных байтов |
| `BATCH_COUNT` | Размер пакета 1..4294967295, по умолчанию 16777216 |
| `MAX_SECONDS` | Неотрицательное десятичное число; 0 означает отсутствие лимита, по умолчанию 0 |
| `DEVICE` | Номер CUDA GPU, по умолчанию 0 |
| `THREADS` | Потоков в блоке: кратно 32, от 32 до 1024, по умолчанию 256; проверяется аппаратный предел GPU |

Байт 0 кандидата заменяет `state[offsets[0]]`, байт 1 — `state[offsets[1]]` и так далее, в порядке little-endian. Остальные байты состояния не меняются. Сам CUDA-исполнитель перебирает **не более 5 байт (40 бит)**; распределения между GPU и автоматического продолжения в нём нет. Для продолжения предусмотрен Python-модуль ниже.

Синтетический пример с нулевым состоянием:

```sh
state_hex=$(printf '%0128d' 0)
./salsa_search blocks "$state_hex" 63 0 1
./salsa_search search "$state_hex" 63 00000000 0 256 256 1 0 256
```

Режим `blocks` выводит полный 64-байтный результат для каждого кандидата; `COUNT` ограничен 256. Он использует тот же примитив Salsa20, что и поиск, и подходит для сравнения с независимой реализацией.

## Результаты и ограничения

Вывод — JSONL: `device`, завершённые пакеты `batch` с массивом `hits`, затем `summary`. В `blocks` выводятся только записи `block` с `candidate` и `hex`. Поиск продолжает работу после совпадений. **Совпадение префикса требует независимой проверки полного содержимого файла.**

Лимит времени проверяется между пакетами, поэтому уже запущенный пакет завершается. Для продолжения возьмите `summary.next_candidate` и уменьшите оставшийся `COUNT`. `batch.elapsed_seconds` измеряет работу GPU; итоговые время и скорость учитывают обслуживание пакетов и вывод. Скорость зависит от GPU и должна измеряться на месте.

Коды возврата: 2 — ошибка аргументов; 3 — ошибка CUDA или вывода; 4 — переполнение буфера из 4096 совпадений. При переполнении выдаётся `type=error`, ошибочный пакет и итоговая сводка не публикуются. Уменьшите `BATCH_COUNT` или используйте более длинный проверяемый префикс. При сбое не считайте весь запрошенный диапазон пройденным: опубликованные ранее пакеты описывают только уже завершённую работу.

## Python API и продолжение поиска

`search_runner.run_search(worker, state_base, unknown_offsets, target, checkpoint_path, *, batch_count=2**28, threads=256, segment_seconds=30, status_callback=None)` возвращает генератор кандидатов. Нужен Python 3.10+ на POSIX-платформе; GPU-исполнитель запускается как дочерний процесс, используется CUDA-устройство 0.

Модуль принимает от 0 до **6 неизвестных байтов**. Для 6 байтов он последовательно фиксирует шестой байт и запускает 256 диапазонов по 40 бит. Поддержка 48 бит не гарантирует практичное время перебора: оно зависит от GPU, проверяемого префикса и последующей проверки совпадений.

Синтетический пример проверяет 256 вариантов последнего байта нулевого состояния:

```python
from contextlib import closing
from pathlib import Path
from search_runner import run_search

with closing(run_search(
    Path("./salsa_search").resolve(),
    bytes(64),
    (63,),
    bytes(64),
    Path("private-checkpoints/demo.json"),
    batch_count=256,
    segment_seconds=1,
)) as candidates:
    for candidate in candidates:
        print("Кандидат:", candidate)
```

Повторный запуск с тем же checkpoint продолжит поиск; несовпадение состояния, смещений или префикса вызывает ошибку. Checkpoint записывается атомарно с `fsync` после обработки всех выданных совпадений пакета. При `break` внутри `with closing(...)` дочерний процесс останавливается, а незавершённый пакет при продолжении проверяется повторно. `segment_seconds` ограничивает отдельный запуск исполнителя, а не весь поиск. Необязательный `status_callback` получает словари прогресса.

**Checkpoint приватен:** он содержит состояние и проверяемый префикс. Храните его отдельно от публикуемого кода. Генератор выдаёт только совпадения потока; для реальных файлов вызывающая программа должна независимо проверять содержимое перед принятием кандидата.
